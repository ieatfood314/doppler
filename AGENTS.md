# doppler

Two shuffle playlists on two keys, synced between computers and a phone. The README says what it does; keep it true when behaviour changes.

## Map

- `doppler/core.py`: the pure rules: playlist ids (`f:<folder path>`, `c:<hex>`, `a:<artist>`, `b:<album>` or `b:<album>\t<album artist>`; artists and albums come from tags, so `playlist_tracks` needs them, and match whatever the case), shuffles (`new_order`, `order_hash`), `reconcile` (fitting a saved shuffle to a folder that changed), `live_position` and `resume_point`, and listening time (`add_listening`, `merge_listening`, `listening_months`, and `year_in_music` for the year's story). `android/.../Core.kt` is a port of it; change both together. `CoreTest.kt` checks the hash against Python's.
- `doppler/library.py`: walks the music folder, reads tags (mutagen, then ffprobe, then the file name), caches them, and serves art. Its rev hashes the tags themselves, so a hub that starts reading a new tag sends every device to fetch the library again; cached entries without that tag must be re-read (see the `albumartist` check in `scan`). `path()` refuses anything outside the library.
- `doppler/hub.py`: the hub (stdlib `http.server`): library, files with Range, art, sessions, custom playlists, slots, moving songs between folders (`/api/tracks/move` moves the files without replacing collisions, rewrites playlist, session and listening references, and keeps old-to-new aliases so late queues and listening uploads follow the move), deleting songs (`/api/tracks/delete` moves the files to the trash with `gio trash`, which on the library's drive is its own `.Trash-<uid>`, and drops them from custom playlists), and the `/api/wait` long poll. State is in `~/.local/share/doppler/hub.json`; listening time is in `listening.json` beside it (it grows by the month, so it isn't rewritten with every position report). Devices send it with their play counts (`listened` in `POST /api/plays`: running totals `{month: {track: [seconds, plays]}}` per install, merged by keeping the larger), `GET /api/listening` sums it per month, and `GET /api/wrapped?year=` sums a year for its story (shown in December and January; `YearHeard.season` and `storyFor` on the phone, `wrapFor` in the window).
- `doppler/player.py`: the desktop daemon. One event thread owns all state, a sender thread reports to the hub, and a watcher long-polls it. It has a local API on `127.0.0.1:4636`, which the CLI and the window use. `mpv.py` is the JSON IPC client, `mpris.py` provides the media keys, and `tray.py` provides the Ayatana AppIndicator tray icon on the same GLib loop.
- `doppler/cli.py`: the `doppler` command. `desktop/Main.qml` is the window, run with `qml6`; it exists only while open.
- `android/`: Kotlin, Compose, Media3. `Engine` is the singleton that owns the player and sync. `PlaybackService` keeps it alive after the task is swiped away. `Speaker` and the `Gate` player are the speaker question. `Listening.kt` keeps the phone's listening time (`Engine` calls `tally` whenever what's sounding might have changed). `Widgets.kt` holds the three widgets (which also load the cover, embedded first, then from the hub) and `WidgetButtons`, the receiver for their back, pause and skip zones; `ScreenTime.kt` holds the 2×2's screen time, which ignition's phone app broadcasts to it (`ca.heeney.ignition.TODAY`) after it sends its screen time, and which doppler asks for with `ca.heeney.ignition.REFRESH`; `ConfirmActivity` is the invisible target of their 1 and 2. A widget only gets taps (the launcher keeps swipes and press-and-hold), so skipping is a tap on an edge and opening a playlist is a tap on the playing number. Its colours are resources with `values-night` twins, never set from code, so the launcher picks day or night. The Nothing launcher lays a 2×2 out at about 177dp and draws it at 158dp, so `widget_square.xml` is sized in those layout units; and a widget can't use the app's fonts, so its text is the system font (Inter on Nothing OS) and `coverSide` measures with `Typeface.DEFAULT`.
- The numerals are drawn, not typeset: a 5 by 7 grid of stars defined three times, in `Dots.kt`, the `DotNumeral` component in `desktop/Main.qml` and `tools/make_art.py` (which writes the widget vectors, the icons and `desktop/doppler.svg`). Change all three together. `make_art.py` also writes the `dots_*` digits and the h and m of the screen time, on the same grid.
- `install.sh`, `update.sh`, `systemd/`: per-user install, no sudo.

## Rules that are easy to break

- **Audio must stay bit-exact.** mpv runs with `--no-config`, volume 100 capped at 100, no ReplayGain, no filters and no pitch correction. ExoPlayer uses float output (keeps 24-bit), with no skip-silence and no normalisation. Never add processing to the signal path; EQ is EasyEffects' job, chosen per playlist.
- **One device plays.** A report with `claim` makes the sender the owner. Non-claim reports from anyone else are answered `superseded`, and that device pauses. Claims come from a press of play (or a playing device reshuffling at the end); heartbeats and track changes never claim. A claim queued offline carries its `age`, so a newer claim elsewhere wins.
- **Reports must be safe to send twice and out of order.** Players queue them while offline and replay them later.
- **The phone never plays from its own speaker without asking**, including from the notification, a headset button or a widget. A yes lasts 10 minutes and is reset when the output changes.
- **The service owns the notification.** `PlaybackService` hands its session to Media3 with `addSession` in `onCreate`, since the app drives ExoPlayer directly and no controller ever asks for it. Without that there's no media notification, no foreground service, and the music dies when the app is swiped away.
- **The phone never streams over mobile data.** Every byte to the hub goes through `Net.kt`: `Hub.request` refuses anything but `progress = true` calls (session reports and the session read before a play) when the phone isn't on unmetered Wi-Fi or Ethernet, and those are metered against 10 MB a month. ExoPlayer's and the notification cover's HTTP goes through `WifiOnlySource`; widget covers check `Net`. A preload waits for Wi-Fi, the playing track gives up, and the engine skips to the next track on the phone. On Wi-Fi means both: the default network (Tailscale's VPN, which copies the metered flag of the network under it) is unmetered, and a real Wi-Fi or Ethernet network is unmetered and validated (Exosphere does the same, since Wi-Fi without internet leaves Android routing over cellular). As a backstop, `Net.downloaded` watches the phone's cellular counter while downloading on Wi-Fi; if it grows by nine tenths of what the app downloads, it treats the phone as off Wi-Fi until a network comes or goes. Any new network call has to go through `Net` too.
- **The playback service must be able to go foreground.** Android only lets an app start a foreground service from the background in a few cases, and without one the process is frozen or killed and the music stops. So `requestPlay` starts `PlaybackService` straight away, while the screen or the widget's tap still counts as the user's doing; `ConfirmActivity` (the widget's target) stays up, invisible and letting taps through, until `starting` is over; and Media3 (1.6 or later) keeps the service foreground for ten minutes after the player stops, errs or ends, so an error retry, a reshuffle at the end or a resume on Wi-Fi doesn't need a fresh start. Don't downgrade Media3 below 1.6.
- **A headset can start it cold.** `MediaButtonReceiver` in the manifest lets a headset's play button (or the system's resume control) start the service after the process has died; `PlaybackService`'s `Resume` callback hands Media3 the queue that `Engine.resumption` works out the same way as a press of play, quickly (the service must go foreground within seconds), and asks instead when it would be the phone's speaker.
- **Say why the music stopped.** Any stop nobody here asked for (focus loss, headphones, a takeover, errors, no Wi-Fi) goes through `Engine.stopped`, which shows it and keeps it for Settings. A track that fails gets one retry (after a fresh look at the phone's files, since Syncthing replacing a file changes its media index id), then is skipped; five failures in a row stop.
- **The phone plays its own copy when it has one.** A queue built before the media index has been read streams every track from the hub for the life of the process, and big FLACs over Tailscale stall. So `play` waits (briefly) for the first scan, and each scan repoints the queued tracks with `useLocal`. A widget tap is often a cold start, because the system frees the app whenever it's idle.
- **The desktop window is optional.** Nothing in the player may depend on it, and it must cost nothing when closed.

## Test

```sh
python3 -m unittest discover -s tests -q
```

```sh
cd android && ./build.sh
```

`build.sh` runs the Kotlin unit tests and builds the signed APK. It needs the toolchain in `~/.local/android-toolchain` and the key in `~/.config/doppler/` (`keystore.properties` and `release.jks`; losing the key means no more in-place updates). `android.properties` there sets the default hub and phone name that get baked into the build.

To try the player without touching a real session, run a throwaway hub with its own `XDG_DATA_HOME` and `XDG_CACHE_HOME` (`bin/doppler serve FOLDER --port 4699`; without them it reads and writes the real hub's `hub.json`), and a player with its own `XDG_CONFIG_HOME` and `XDG_STATE_HOME`, plus `daemon --mpv=--ao=null`. Release builds default to the real hub, so point a test phone or emulator at the throwaway one in Settings before pressing play.

## Ship

1. Run the tests, commit, then push to `main` (public: `github.com/ieatfood314/doppler`).
2. The hub runs from `~/repos/doppler` (on `main`) as the user unit `doppler-hub.service`. After pushing from a worktree, `git -C ~/repos/doppler pull --ff-only` first (it has been left commits behind), then `systemctl --user restart doppler-hub`.
3. Computers run a clone in `~/.local/share/doppler/app`. Run `update.sh` there after a player or window change.
4. After a change under `android/`, run `android/release.sh "what changed"`. It builds from the pushed commit and creates the GitHub release `v1.0.<commit count>`; the phone picks it up through Obtainium.
